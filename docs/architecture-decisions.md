# Twick Hub — Architecture Decisions (FASE 0)

**Estado:** Congelado en FASE 0 · **Basado en:** Master Plan v3.0 + auditoría de TwitchLink 3.5.5 (repo original devhotteok/TwitchLink, subido como referencia)

Formato ADR ligero: contexto → decisión → consecuencias. Estas decisiones son vinculantes para las fases siguientes salvo que una fase futura las revise explícitamente y lo documente aquí (Master Plan §32).

## AD-01 — Punto de partida: repo vacío, sin código heredado de Twick Hub
**Contexto:** No existe ningún repositorio parcial de Twick Hub. Solo se dispone del Master Plan v3.0 y de TwitchLink 3.5.5 vanilla como referencia.
**Decisión:** FASE 0 audita exclusivamente TwitchLink 3.5.5 como fuente de comportamiento/UX a preservar. FASE 1 construye el skeleton desde cero.
**Consecuencias:** El "estado real del repositorio actual" que pide el Master Plan §34 es, en este caso, el estado de 3.5.5 — ver `docs/migration-map.md`.

## AD-02 — PySide6 + QML confirmado, sin alternativa QWidgets
**Contexto:** 3.5.5 usa PyQt6 + QtWidgets + 28 archivos `.ui` (Qt Designer). El Master Plan exige evaluar PySide6+QML vs PySide6+QWidgets.
**Decisión:** Se mantiene PySide6 + QML. QWidgets se descarta: no resolvería el problema de mantenibilidad/extensibilidad que motiva el rewrite.
**Consecuencias:** Ninguno de los 28 `.ui` ni de los 49 archivos de `Ui/*.py` de 3.5.5 se reutiliza como implementación (costo alto, ver RISK-UI-01 en risk-register.md) — se reutiliza comportamiento/flujo, no código.

## AD-03 — Eliminar el patrón `App.Instance`
**Contexto:** `Core/App.py` crea `Instance = App(...)` como efecto secundario del *import* del módulo, y cuelga de él ocho servicios más (`NetworkAccessManager`, `TwitchGQL`, `Translator`, `NotificationManager`, `ContentManager`, `TempManager`, `ImageLoader`, `PartnerContentManager`), también instanciados al importar. `App.Instance` se referencia directamente en al menos 14 archivos.
**Decisión:** Confirma Master Plan §5 sin cambios: estos servicios pasan a `bootstrap/container.py`, inyectados por constructor.
**Consecuencias:** Es el hallazgo de mayor impacto de FASE 0 para FASE 1 — el skeleton debe demostrar arranque/cierre limpio sin ningún objeto creado por efecto secundario de import.

**Corolario (FASE 1, verificado empíricamente):** `Application` no crea su propio `QGuiApplication` — lo recibe por constructor. Qt solo permite una instancia de `QGuiApplication` por proceso (confirmado por un `RuntimeError` real de shiboken al correr la suite de tests: dos tests que cada uno creaba la suya chocaban entre sí). `main.py` construye la instancia una sola vez y se la pasa a `Application`; los tests inyectan la instancia de sesión de `pytest-qt` (`qapp`) en vez de crear la suya. Mismo principio que el resto de AD-03 — nada se construye a través de un global, todo se recibe explícitamente — aplicado a un objeto de Qt que además tiene la restricción física de "uno por proceso".

## AD-04 — Twitch: EventSub por WebSocket, con credencial de aplicación separada de la de usuario
**Contexto:** El PubSub heredado de Twitch fue apagado permanentemente el 14 de abril de 2025 — no es una preferencia arquitectónica, es un hecho verificado: `Services/Twitch/PubSub/*` de 3.5.5 ya no puede conectar a Twitch. El presupuesto de coste de EventSub por token de usuario (`max_total_cost=10`, ~1 de coste por suscripción a un canal ajeno) limita a ~3–5 canales monitoreables en tiempo real por token de usuario — insuficiente para una lista de favoritos típica.
**Decisión:** `TwitchEventSubProvider` usará dos credenciales separadas: (1) el token de usuario actual, extraído de sesión de navegador, para GQL privado/Integrity/reproducción/descarga; (2) un client_id/secret propio de Twick Hub (app registrada en Twitch) para EventSub, a validar en FASE 4d si el transporte WebSocket acepta tokens de aplicación o exige Webhooks (que requerirían endpoint público, indeseable en una app de escritorio).
**Consecuencias:** Es el mayor riesgo técnico abierto del proyecto — ver RISK-TWITCH-01 en risk-register.md. Mitigación de respaldo: Helix `Get Streams` en polling de bajo coste para favoritos que excedan presupuesto.
**Corrección (FASE 4d):** La documentación oficial de EventSub confirma que el transporte WebSocket exige un token de **usuario** para crear subscriptions — los tokens de aplicación son el camino de Webhooks (servidor-a-servidor), que este proyecto no tiene ni quiere montar solo para esto (sería el "backend remoto solo por comodidad" que el propio Master Plan prohíbe). Se descarta la idea de una credencial de aplicación separada para EventSub — `TwitchEventSubProvider` usa el mismo token de usuario de FASE 4a. El techo de RISK-TWITCH-01 (~5 canales) es real, no una hipótesis a resolver con ingeniería — ver AD-23.

## AD-05 — Kick: capacidades oficiales primero, VOD/Clips fuera del core
**Contexto:** La API pública oficial de Kick (`api.kick.com/public/v1`, OAuth 2.1+PKCE, activa desde ~mayo 2026) cubre Users, Channels, Chat, Livestreams, Moderation, Rewards, Categories y Events. No se encontró VOD ni Clips en la superficie pública — el acceso conocido (incluida la app Android oficial de Kick) pasa por `api.kick.com/private/v1/...`, no oficial.
**Decisión:** FASE 5 implementa primero Auth/Users/Channels/Streams/Categories sobre la API oficial. VOD/Clips/Download de Kick se implementan como `KickUnofficialAdapter`: aislado, marcado como no oficial en la UI, desactivable.
**Consecuencias:** La paridad funcional completa con Twitch puede no alcanzarse para Kick en FASE 5; se comunica explícitamente en la UI (capacidades ausentes ocultas/deshabilitadas, Master Plan §9).

## AD-06 — Live monitoring de Kick: polling adaptativo oficial, no webhook público
**Contexto:** El mecanismo de eventos en tiempo real documentado de Kick exige una URL de webhook pública configurada en el dashboard de desarrollador — no encaja con una app de escritorio sin backend propio.
**Decisión:** Opción B del Master Plan §13: polling adaptativo oficial sobre `Livestreams` (funciona con token de usuario o de aplicación, sin scope especial, hasta 50 `broadcaster_user_ids` por llamada), no la opción A (webhook + infraestructura pública).
**Consecuencias:** FASE 10 implementa backoff/agrupación de este polling. Si Kick ofrece en el futuro un transporte push sin endpoint público, esta decisión se revisita.

## AD-07 — Credenciales vía OS keyring, confirmado por hallazgo concreto en 3.5.5
**Contexto:** `AppData/Preferences.py` serializa `Account.__save__()` (incluye el `OAuthToken` del usuario) dentro del árbol que `json.dump()` vuelca completo a `settings.json`, sin cifrado visible en `EncoderDecoder.py`. Es un hallazgo verificado en el código, no una suposición.
**Decisión:** Confirma Master Plan §14 sin cambios — tokens vía `keyring`, nunca en `settings`/SQLite.
**Consecuencias:** FASE 15 (Legacy Migration) debe leer el token viejo de `settings.json` una vez para migrarlo al keyring y luego purgarlo del JSON legacy, no solo dejar de escribir ahí en adelante.

## AD-08 — Selenium/Patchright: se mantienen, carga bajo demanda
**Contexto:** Uso confirmado y acotado a `Services/Account/BrowserCookieDetector/*` y `ExternalBrowserDriver.py` — no está esparcido por el resto de la app. Solo existe detector de Firefox; no hay detector de Chrome/Chromium en 3.5.5.
**Decisión:** Se mantienen (Master Plan §28 lo permite si se justifica), pero como dependencia de import perezoso, aislada en Infrastructure, no cargada en el arranque.
**Consecuencias:** Afecta tamaño de paquete — ver RISK-PKG-01. Evaluar en FASE 4a si conviene sumar Chrome/Chromium.

## AD-09 — PartnerContent: pospuesto
**Contexto:** 3.5.5 tiene un sistema de contenido de socio/patrocinado (`Services/PartnerContent/*`) con caché por referencia de widget.
**Decisión:** POSPONER (una de las tres opciones que exige Master Plan §29). Se decide antes de FASE 2 porque afecta si la UI reserva espacio para este contenido.
**Consecuencias:** Ninguna hasta FASE 2.

## AD-10 — Empaquetado inicial: Windows confirmado, macOS por decidir en FASE 19
**Contexto:** `resources/dependencies/` de 3.5.5 solo empaqueta FFmpeg para `windows/` y `macos/` — no hay binario Linux. PyInstaller ya es la herramienta usada.
**Decisión:** Windows x64 es el target confirmado desde FASE 1. Windows+macOS-desde-el-inicio vs. macOS-después queda explícitamente abierto para FASE 19 (Master Plan §30) — FASE 0 no fuerza esa decisión.
**Consecuencias:** Ninguna hasta FASE 19.

## AD-11 — Theme/Navigation/Toast como QML singletons vía `@QmlElement`/`@QmlSingleton` (FASE 2)
**Contexto:** El shell necesita estado compartido con QML (tema activo, página actual, cola de toasts) sin recurrir a un service locator. PySide6 6.x ofrece registro de tipos QML declarativo vía los decoradores `@QmlElement`/`@QmlSingleton` de `PySide6.QtQml` — probado aislado antes de construir el resto del shell encima.
**Decisión:** `presentation/qml_bridge/{theme,navigation,toast}.py` exponen `Theme`, `NavigationController` y `ToastController` así. `bootstrap/application.py` importa `presentation.qml_bridge` antes de cargar cualquier QML — el import ejecuta los decoradores y registra los tipos; sin ese import, `import TwickHub 1.0` fallaría en QML.
**Consecuencias:** Es el único patrón "global" permitido — no es un service locator porque QML lo resuelve por el sistema de tipos de Qt, no por lookup manual de código Python; nada en Domain/Application lo toca (`presentation/qml_bridge` es exclusivamente de la capa Presentation). `ToastController` solo emite la señal `toastRequested`; la lista visible de toasts vive en `ToastHost.qml`, no en Python — es puro estado de presentación transitorio, sin significado de negocio.
**Nota de stubs:** el stub de tipos de PySide6 no modela bien `Property()` en forma funcional ni `qmlTypeId()` con argumentos `str` (ambos funcionan correctamente en runtime, verificado). Los tests que topan con esto llevan `cast()`/`pyright: ignore` puntuales y comentados — ver `tests/test_theme.py` y `tests/test_qml_shell.py`.

## AD-12 — Paleta del shell: identidad propia, ni Twitch ni Kick
**Contexto:** El Master Plan no fija paleta de colores (verificado — no hay ninguna sección al respecto). Twitch (morado `#9147FF`) y Kick (verde `#53FC18`) son ambas plataformas de primera clase (AD-05); usar el color de marca de una como acento del propio shell implicaría favoritismo visual hacia esa plataforma.
**Decisión:** El shell usa una paleta neutra propia (grafito frío en dark, casi-blanco cálido en light) con un acento ámbar (`#E8A33D`) que no es ni Twitch ni Kick. Los colores de marca de cada plataforma aparecen únicamente en `PlatformBadge.qml` — nunca en la chrome de la app (sidebar, header, fondos).
**Consecuencias:** Si una fase futura agrega una tercera plataforma, no requiere retocar la paleta del shell — solo agregar su color de badge correspondiente.

## AD-13 — Entidades de dominio: dataclasses congeladas + `Media` como referencia polimórfica ligera
**Contexto:** FASE 3 exige 14 entidades (Channel, User, Stream, Video, Clip, Media, Download, DownloadJob, DownloadSegment, Favorite, Playlist, ScheduledDownload, Notification, PlatformAccount) más enums/value objects/protocols/use cases, sin PySide6 ni ningún framework.
**Decisión:** Todas las entidades y value objects son `@dataclass(frozen=True, slots=True)` — inmutables, actualizaciones vía `dataclasses.replace()` o un método que devuelve una instancia nueva (p. ej. `Playlist.with_item_added`), nunca mutación in-place. `Media` no es una entidad con historia propia sino un value object polimórfico (`kind`, `ref`, `title`, `channel_ref`, `thumbnail_url`, `duration`) que `Download`, `Favorite`-adyacentes (`PlaylistItem`), y `Notification` usan para apuntar a "contenido" sin importar si es un Stream, Video o Clip. `Download` (registro persistente/UI) se separa de `DownloadJob`+`DownloadSegment` (unidades de ejecución del motor de FASE 7) — un Download puede sobrevivir a varios intentos de Job sin que la UI necesite saberlo.
**Consecuencias:** Favorites/Playlists/Notifications no necesitan tres campos opcionales (`stream_id`, `video_id`, `clip_id`) ni un `Union[Stream, Video, Clip]` — un solo campo `Media` cubre los tres casos. `PlatformRef` (platform + external_id) es la identidad natural para todo lo que viene de una plataforma (Channel, User, Stream, Video, Clip); las entidades puramente locales (Download, Favorite, Playlist, ScheduledDownload, Notification) generan su propio `id` (UUID) porque no existen en ninguna plataforma.

## AD-14 — Protocols de plataforma segregados, no un `PlatformClient` único
**Contexto:** docs/risk-register.md (RISK-TWITCH-03) ya nombraba `VideoProvider`/`ClipProvider` como el límite de aislamiento para la API GQL no oficial de Twitch. docs/kick-audit.md confirmó que la API oficial de Kick no cubre VOD/Clips.
**Decisión:** `domain/protocols.py` define protocols angostos y específicos (`ChannelDirectory`, `LiveStreamProvider`, `VideoProvider`, `ClipProvider`, `PlaybackResolver`, `LiveMonitor`) en vez de una única interfaz "PlatformClient" que fuerce a cada adapter a implementar métodos que no puede soportar. Un adapter de Kick (FASE 5) puede implementar `ChannelDirectory`+`LiveStreamProvider` sin verse obligado a fingir `VideoProvider`/`ClipProvider` mientras Kick no los oficialice.
**Consecuencias:** El código de Application (casos de uso) que dependa de `VideoProvider` simplemente no es aplicable a un platform que no lo implementa — eso se resuelve en FASE 5/6 (capa de plataforma unificada), no en FASE 3. Todos los métodos de protocol son `async def`: ninguna implementación real (HTTP, SQL) puede bloquear el hilo de UI, regla permanente del Master Plan.

## AD-15 — Auth de Twitch implementada: dos credenciales, `/oauth2/validate` en vez de GQL
**Contexto:** FASE 4a implementa lo que AD-04 solo había diseñado. Prohibición explícita del Master Plan §38: "No implementar GraphQL completo todavía" — necesitaba una forma de saber a quién pertenece el token de sesión sin GQL.
**Decisión:** `infrastructure/twitch/account_service.py` usa el endpoint oficial y documentado `GET https://id.twitch.tv/oauth2/validate` (devuelve `login`/`user_id`/`expires_in`) para identificar la cuenta — no toca GQL. `infrastructure/twitch/app_token_provider.py` implementa el flujo separado de AD-04 (client credentials) para el futuro token de aplicación de EventSub, con caché y refresh automático por expiración. `AccountProvider` (nuevo protocol en `domain/protocols.py`, agregado en esta fase) es lo que `TwitchAccountService` implementa — `connect`/`disconnect`/`current_account`.
**Consecuencias:** FASE 4b construye el cliente GQL completo sobre esta base sin tocar la lógica de autenticación ya resuelta aquí.

## AD-16 — Integrity: se captura la cabecera real de Twitch, no se calcula
**Contexto:** Al portar `IntegrityGenerator.py` de 3.5.5 se confirmó que el mecanismo no calcula ni falsea nada — carga la página de cuenta de Twitch en un `QWebEnginePage` oculto, deja correr el JavaScript real y sin modificar de Twitch, e intercepta la petición real que ese JS genera hacia `INTEGRITY_URL`, capturando sus cabeceras para reenviarlas él mismo (con el token del usuario agregado). El cómputo anti-bot ocurre enteramente dentro del código de Twitch, no en este proyecto.
**Decisión:** Se porta el mecanismo tal cual (`infrastructure/twitch/integrity_adapter.py`), adaptado a PySide6 e inyección de dependencias (sin `App.Instance`).
**Verificación honesta:** `QtWebEngineCore` importa y `QWebEngineProfile` se construye en el sandbox de esta fase. Cargar la página real y capturar un token no pudo verificarse acá — ni por red (dominios de Twitch fuera de la lista permitida de este sandbox) ni por Chromium, que rechaza correr su renderer como root sin `--no-sandbox` (error real confirmado al probarlo). Corroborar en una máquina real con sesión de Twitch real antes de que FASE 4d dependa de esto — coincide con lo que RISK-TWITCH-04 ya anticipaba (mantenimiento continuo, no algo que se arregla una vez).

## AD-17 — `CookieImporter` es un protocol de Infrastructure, no de Domain
**Contexto:** `TwitchAccountService` necesita depender de una abstracción para importar cookies del navegador (para poder testear con un fake, y para poder sumar Chrome/Chromium después — AD-08), pero esta capacidad es específica de cómo Twitch obtiene su token de sesión, no algo que Kick o cualquier otra plataforma necesite de la misma forma.
**Decisión:** `CookieImporter` vive en `infrastructure/twitch/browser_cookie_import.py`, no en `domain/protocols.py`. No todo protocol necesita vivir en Domain — solo lo que Application o varias plataformas necesitan cruzar el límite de Domain para usar.
**Consecuencias:** Mantiene `domain/protocols.py` enfocado en lo que de verdad es multiplataforma (AD-14), sin inflarlo con detalles de implementación de un solo adapter.

## AD-18 — Queries GQL portadas literalmente; Integrity solo en las operaciones que de verdad lo piden
**Contexto:** Al auditar `TwitchGQLOperations.py`/`TwitchGQLAPI.py` de 3.5.5 para FASE 4b se confirmó que las operaciones de metadata (GetChannel, GetChannelVideos, GetChannelClips, GetVideo, GetClip) son GraphQL normal — texto de query real, no hashes de persisted query — a diferencia de las tres operaciones de playback (persisted query + Integrity + auth de usuario), que son FASE 4c y no se tocan acá. `useIntegrity` solo es `True` para `GetChannelVideos`/`GetChannelClips`; `GetChannel`/`GetVideo`/`GetClip` no lo necesitan, y ninguna operación de esta fase necesita el token OAuth del usuario.
**Decisión:** `infrastructure/twitch/gql/operations.py` porta las cinco queries de metadata tal cual, con `OPERATIONS_REQUIRING_INTEGRITY` marcando exactamente esas dos. `TwitchGQLClient` depende de un `IntegrityHeaderSource` (protocol angosto, no el `IntegrityAdapter` completo) para poder testear sin QWebEngine.
**Consecuencias:** FASE 4c reutiliza `TwitchGQLClient` sin cambios — solo agrega las operaciones de playback y, ahí sí, el token de usuario.

## AD-19 — Resolución id→login para listar videos/clips; `mappers.py` es el único lugar que ve el schema de Twitch
**Contexto:** `PlatformRef` usa el id numérico de Twitch como identidad canónica (AD-13, porque el login puede cambiar), pero `GetChannelVideos`/`GetChannelClips` solo aceptan `login`, no `id`.
**Decisión:** `TwitchVideoProvider`/`TwitchClipProvider` reciben un `ChannelDirectory` y resuelven id→login antes de listar, en vez de cambiar qué guarda `PlatformRef`. Todo el mapeo de dict de GQL (`displayName`, `lengthSeconds`, nodos anidados) a entidades de Domain vive únicamente en `infrastructure/twitch/gql/mappers.py` — es el límite real de "no mezclar API con Domain" del Master Plan §39: Domain nunca ve una forma de dato de Twitch, ni GQL nunca importa nada de `domain/`.
**Consecuencias:** Un futuro adapter de Kick (FASE 5) puede resolver su propio id→handle de la misma forma si su API lo exige, sin que `PlatformRef` ni ningún caso de uso de Application se enteren de la diferencia.

## AD-20 — Playback separado de metadata y de download; token+manifest, sin tocar bytes de video
**Contexto:** Master Plan §40 exige separar explícitamente "API metadata / Playback / Download". Las 3 operaciones de playback (persisted query, `useIntegrity=True`, `useAuth=True`) eran justo lo que FASE 4b dejó pendiente a propósito.
**Decisión:** `infrastructure/twitch/playback/` es un paquete aparte de `infrastructure/twitch/gql/` (FASE 4b) — comparte `TwitchGQLClient` (extendido con `send_persisted`/`send_persisted_batch`, sin romper `send()` de FASE 4b) pero no toca `channel_directory.py`/`video_provider.py`/`clip_provider.py`. `TwitchPlaybackResolver.resolve()` devuelve una `PlaybackSource` (URL + etiqueta de calidad) — nunca descarga ni escribe un byte; eso sigue siendo FASE 7.
**Consecuencias:** El mismo `TwitchGQLClient` seguirá sirviendo para FASE 4d (EventSub) si hace falta, sin duplicar la lógica de headers/Integrity.

## AD-21 — Subscriber-only confirmado: es el `reason` exacto del propio token de Twitch
**Contexto:** docs/functional-baseline.md dejó pendiente confirmar en FASE 4c cómo se detecta un video solo-para-suscriptores.
**Decisión:** Se confirma el mecanismo exacto (portado de `_validateToken` de 3.5.5): el playback token, decodificado, trae `authorization.forbidden=true` con `authorization.reason="UNAUTHORIZED_ENTITLMENTS"` específicamente para este caso — `SubscriberOnlyRestrictedError` en `playback/errors.py` distingue este reason exacto de cualquier otro `forbidden` (que cae en `PlaybackForbiddenError`, genérico, porque no hay confirmación de qué otros reasons existen — no se inventan significados no verificados).
**Consecuencias:** docs/functional-baseline.md puede marcar esta fila como confirmada — ver ahí.

## AD-22 — SSAI: respuesta parcial, no la pregunta completa de RISK-TWITCH-02
**Contexto:** El campo `hideAds` de `StreamPlaybackAccessToken` en 3.5.5 sí revela cuándo Twitch no muestra anuncios a un viewer específico (Turbo o beneficio de sub ad-free).
**Decisión:** Se porta `stream_hides_ads()` y se registra su resultado, pero no se usa para tomar ninguna decisión todavía (no hay pipeline de descarga real aún — eso es FASE 7). No se declara resuelto RISK-TWITCH-02: este campo solo confirma cuándo un viewer específico NO tiene el problema; no dice nada sobre qué hay en los segmentos para quien sí los recibe.
**Consecuencias:** FASE 7 (Download Engine) es quien realmente necesita decidir qué hacer con `hideAds`/SSAI al procesar segmentos — ver docs/risk-register.md RISK-TWITCH-02, actualizado con esta precisión.

## AD-23 — El techo de EventSub se aplica de verdad, no se documenta y ya
**Contexto:** RISK-TWITCH-01 identificó el techo de ~5 canales (`floor(10/2)`, dos tipos de subscription por canal) desde FASE 0. Implementarlo sin aplicarlo dejaría que el código intente suscribir un sexto canal y falle de forma confusa contra la API real.
**Decisión:** `CapacityGovernor` (`infrastructure/twitch/eventsub/capacity.py`) rechaza explícitamente con `CapacityExceededError` antes de intentar la subscription — nunca deja que Twitch sea quien lo descubra. `TwitchEventSubProvider.subscribe()` libera la reserva si la creación de la subscription falla, para que un fallo no deje presupuesto "fantasma" ocupado.
**Consecuencias:** FASE 10 (Live Monitor) es quien decide qué hacer con favoritos más allá del techo (polling Helix de bajo coste, ya previsto como mitigación) — esta fase solo garantiza que el límite nunca se viola en silencio.

## AD-24 — Bus de eventos interno en Domain, EventSub nunca toca UI
**Contexto:** Master Plan §41 exige "conectar OFFLINE → ONLINE mediante eventos internos" y "no conectar EventSub directamente con UI."
**Decisión:** `domain/events.py` agrega `ChannelWentOnline`/`ChannelWentOffline` + un `EventBus` mínimo (suscribir/publicar, sin frameworks). `TwitchEventSubProvider` publica ahí — no conoce ni le importa quién escucha. Nadie escucha todavía (eso es FASE 9/10/11); esta fase solo construye el bus y publica.
**Consecuencias:** Cuando FASE 10 conecte Favoritos/Notificaciones al bus, no necesita tocar nada de `infrastructure/twitch/eventsub/`.

## AD-25 — `_receive_and_handle_one` como unidad de trabajo testeable, separada del loop infinito
**Contexto:** Un cliente WebSocket real corre en un loop infinito (`run_forever`), difícil de testear de forma determinista sin correr una tarea de fondo real.
**Decisión:** Toda la lógica (recibir, dedupe, despachar por tipo, reconectar ante corte anormal) vive en `_receive_and_handle_one()`, una corrutina que procesa exactamente un mensaje y retorna. `run_forever()` es un `while True` de una línea que la llama. Los tests llaman `_receive_and_handle_one()` directamente con una conexión falsa que entrega mensajes guionados — sin tareas de fondo, sin timing real.
**Consecuencias:** Encontrado real durante la implementación: la primera llamada tras conectar consume el mensaje de bienvenida Y el primer mensaje real en la misma llamada — documentado en los tests, no es un bug.

## AD-26 — OAuth de Kick: listener HTTP local de un solo uso, no esquema de URI personalizado
**Contexto:** Kick usa OAuth 2.1 + PKCE real (a diferencia de Twitch, que no tiene flujo OAuth propio para este proyecto — ver AD-04/AD-15). Una app de escritorio necesita recibir el redirect del navegador de alguna forma.
**Decisión:** `infrastructure/kick/redirect_listener.py` levanta un servidor HTTP local de un solo uso (`http.server` en un hilo, coordinado con asyncio vía `call_soon_threadsafe`) en `localhost` — no un esquema de URI personalizado (`twickhub://...`), que exige registro específico por sistema operativo y no lo pide la documentación de Kick. `RedirectListener` es un protocol angosto para poder testear sin navegador real.
**Consecuencias:** Verificado de punta a punta en esta fase con una petición HTTP real (no mockeada) contra el listener — es el test más directo de todo el proyecto hasta ahora, porque no depende de que Kick sea alcanzable.

## AD-27 — `KickUnofficialAdapter` pospuesto, no implementado en FASE 5
**Contexto:** Master Plan §42: "Solo implementar estas capacidades [VOD/clips/playback/download] si están validadas." docs/kick-audit.md reconfirma con evidencia más fuerte que en FASE 0 que VOD/Clips siguen sin oficializarse.
**Decisión:** No se construye `KickUnofficialAdapter` esta fase. ## AD-33 — Arquitectura de segmentos: total desconocido por defecto, `segments_completed_of()` como respaldo
**Contexto:** Un VOD/clip conoce su lista completa de segmentos tras una sola lectura de playlist; un directo (`stream`) no conoce su total hasta que termina. `DownloadExecutor` no distingue de antemano cuál es cuál sin leer primero.
**Decisión:** `DownloadExecutor` siempre llama `progress.start(download_id, total_segments=None)` — igual para VOD que para directo — así que `ProgressTracker.progress_of()` devuelve `0.0` durante toda la descarga en ambos casos por ahora. `segments_completed_of()` (cuenta cruda, siempre funciona) queda como vía de escape para una fase de UI futura que quiera mostrar "N segmentos descargados" en vez de un porcentaje.
**Consecuencias:** Reportar porcentaje real para VOD (detectando que el primer batch ya trae `is_complete=True` y fijando el total entonces) es una mejora incremental, no una reescritura — queda pendiente, registrada en `docs/risk-register.md`, no implementada aquí para no ampliar el alcance de FASE 7 sin necesidad.

## AD-34 — Cancelación verificada también después del loop de polling, no solo vía excepción
**Contexto:** `SegmentManager` señaliza cancelación lanzando `DownloadCancelledError`, pero `HlsPlaylistReader.poll_until_complete`'s `should_stop` (=`is_cancelled`) puede cortar el loop de polling *sin* que `SegmentManager` llegue a lanzar nada — por ejemplo si la cancelación llega entre un poll y el siguiente, sin ningún segmento en vuelo. Descubierto durante el testing de esta misma fase (`test_cancellation_mid_download_stops_the_pipeline` falló en el primer intento: el download terminaba en `COMPLETED` con contenido parcial).
**Decisión:** `DownloadExecutor.run()` verifica `is_cancelled()` explícitamente otra vez justo después de que el `async for` del polling termina, antes de pasar a `PROCESSING` — sin importar si el loop terminó por agotarse (VOD completo) o por cancelación silenciosa.
**Consecuencias:** Cualquier futura fuente adicional de "corte silencioso" del loop de polling (por ejemplo, un límite de duración máxima) debe pasar por el mismo chequeo explícito post-loop, no asumir que una excepción siempre se propaga.

## AD-35 — Pausa/reanudación: el estado visible lo fija `DownloadService`, no el worker bloqueado
**Contexto:** Master Plan §44 exige el estado `PAUSED` y tests de pausa. El worker que ejecuta un `Download` puede estar bloqueado dentro de `SegmentManager._wait_while_paused` en el momento exacto en que se solicita la pausa — no puede "darse cuenta" y actualizar su propio estado en ese instante.
**Decisión:** `DownloadService.pause()`/`.resume()` actualizan `Download.status` inmediatamente y por su cuenta (independientemente de dónde esté el worker), y además marcan/limpian una bandera en `JobControlStore` que `SegmentManager` sondea cooperativamente. El worker no se cancela ni se vuelve a encolar al pausar: simplemente se queda bloqueado en el mismo punto y continúa exactamente ahí al reanudar — sin necesidad de un mecanismo de reanudación-desde-cero para el caso "misma sesión de la app".
**Consecuencias:** Si la app se reinicia mientras un download está `PAUSED`, el worker en memoria ya no existe — reanudar después de un reinicio requiere invocar `DownloadExecutor.run()` de nuevo desde cero, lo cual funciona para segmentos ya descargados (se saltan, ver `SegmentManager`) pero no puede funcionar para un directo que ya terminó mientras tanto (su URL de reproducción ya no es válida). Registrado como RISK-RESUME-01, no resuelto aquí — no estaba en el alcance de FASE 7 (que no pide recuperación tras caída, eso es más cercano a "safe shutdown" de FASE 8).

## AD-37 — Persistencia se queda con SQLAlchemy síncrono, envuelto en `asyncio.to_thread`
**Contexto:** FASE 1 ya construyó `Container.engine`/`session_factory` como SQLAlchemy **síncrono** (`create_engine`, `sessionmaker`, no `create_async_engine`/`AsyncSession`), y `bootstrap/application.py::Application._shutdown()` ya llama `self._container.engine.dispose()` de forma síncrona en su `finally:` de cierre. `pyproject.toml` no tiene `aiosqlite` como dependencia. **Consecuencias:** RISK-ARCH-01 (FASE 6, "PlatformRegistry sin wirear") sigue abierto — wirear adapters reales de Twitch/Kick requiere credenciales/config que este entorno no tiene. Solo la mitad de persistencia quedó resuelta aquí; el resto de los seis repositorios (channels, downloads, playlists, scheduled_downloads, notifications) sigue sin wirear a `Container` hasta que la fase que los necesite lo pida — mismo criterio que Favorites: wirear solo lo que la fase actual usa de verdad, no todo de una vez "por si acaso".

## AD-51 — Live Monitor: push + reconcile lento + fallback rápido; sondeo siempre por lotes (FASE 10)
**Contexto:** §47 exige "preferir push/eventos oficiales antes que polling" y, si se sondea, "adaptativo; backoff; agrupación; reducción". RISK-TWITCH-01 dejó abierto qué pasa con los favoritos más allá de las 5 plazas de EventSub, y AD-06 fijó el sondeo adaptativo oficial para Kick.
**Decisión:** Un `LiveMonitor` por plataforma (el que ya expone `PlatformAdapters.live_monitor`). Kick: `PollingLiveMonitor` sobre `KickBatchLiveStatusProvider` (`GET /livestreams`, ≤50 ids por request). Twitch: `HybridLiveMonitor` con tres roles — **push** (EventSub, los primeros canales que caben, en orden de suscripción; costo de sondeo 0), **reconcile** (un `PollingLiveMonitor` lento, base 900 s, sobre *los mismos* canales push) y **fallback** (un `PollingLiveMonitor` rápido, base 60 s, sobre los canales que no caben), ambos contra `TwitchBatchLiveStatusProvider` (Helix `GET /streams`, ≤100 ids). El reconcile existe porque EventSub solo entrega *transiciones*: no da el estado inicial, no repite lo perdido durante una desconexión y no reintenta un `stream.online` cuyo detalle no pudo obtenerse. Cuando se libera una plaza push (se quita un favorito) se promueve el canal sondeado más antiguo; una suscripción revocada por Twitch degrada ese canal a fallback.
**Consecuencias:** Costo medido (sintético, ver `benchmarks/live_monitor_bench.py`): 20 favoritos de Twitch ≈ 26 requests de sondeo/hora (+10 suscripciones EventSub únicas) frente a 1200/h del sondeo ingenuo por canal. Kick: ≈23–39 requests/h para cualquier cantidad ≤50 de favoritos. `PlatformAdapters`/`PlatformCapabilities` no cambian.

## AD-52 — `LiveStateTracker` es el único publicador de eventos de directo
**Contexto:** Varios backends pueden observar el mismo canal en momentos distintos (push, reconcile, fallback, o un canal que migra entre ellos). Si cada uno publicara, los consumidores (FASE 11+) recibirían cada go-live varias veces.
**Decisión:** `application/live_monitor/tracker.py`. Los backends solo *observan* (`observe_live`/`observe_offline`); el tracker compara con lo que ya sabía y publica en el bus **público** solo transiciones reales. `TwitchEventSubProvider` (FASE 4d) sigue publicando en un bus — pero ahora uno **privado** que el tracker escucha (`tracker.attach(private_bus)`); sin cambios en el provider por esto. Primer avistamiento offline no emite nada; `forget()` (favorito quitado) descarta el estado sin emitir.
**Consecuencias:** El cableado (quién crea qué bus) es responsabilidad del composition root — pendiente, ver RISK-ARCH-05.

## AD-53 — Formato real de `/livestreams` de Kick: la clave `broadcaster_user_id` repetida (corrige docs/kick-audit.md)
**Contexto:** `kick-audit.md` (FASE 0) anotó "`broadcaster_user_ids` (máx. 50)" — el nombre del *argumento* del SDK de Rust, no del parámetro HTTP.
**Decisión:** Verificado en FASE 10: el changelog de KickDevDocs ("28/07/2025 — Allow multiple broadcaster_user_id params on livestreams") y el código fuente del crate `kick-api` (`request.query(&[("broadcaster_user_id", id)])` una vez por id) confirman que el formato es la **misma clave repetida**. `KickAPIClient.get_livestreams` la envía así (test explícito: no coma-separado, no `..._ids`). El máximo de 50 viene de la documentación de ese SDK, no de un texto oficial de Kick leído directamente — sigue siendo la parte menos verificada; ante un rechazo, bajar `MAX_IDS_PER_REQUEST` es un cambio de una línea.
**Consecuencias:** `kick-audit.md` actualizado. Un 429 de Kick ahora se distingue (`KickRateLimitedError`, subclase de `KickAPIError` — los `except` existentes siguen valiendo) y lleva `Retry-After` solo si es numérico.

## AD-54 — Política de sondeo adaptativo; valores por defecto PROVISIONALES
**Contexto:** §47 pide backoff y "reducción cuando corresponda". Los límites oficiales de Kick siguen sin confirmarse (`kick-audit.md`) y ninguna plataforma es alcanzable desde el sandbox.
**Decisión:** `AdaptiveInterval` (puro, determinista, `rng` inyectable): (1) **backoff** exponencial por fallo consecutivo hasta un tope; un `retry_after` de la plataforma es un mínimo inviolable (acotado a 1 h para que un servidor defectuoso no aparque el monitor); (2) **estiramiento en calma**: tras 5 polls sin novedad el intervalo crece ×1.5 hasta 180 s, y cualquier novedad lo devuelve a la base; (3) **jitter** solo alargando (0–10 %), para que un `retry_after` nunca se acorte. Sin canales el monitor **no tiene ningún temporizador**: espera un `asyncio.Event`. Una ráfaga de suscripciones se agrupa (1 s) en un solo request. Se descartó un "modo background" con multiplicador: monitorear es justamente la tarea que el usuario pidió (§7), y no había evidencia de que hiciera falta.
**Consecuencias:** 60/180/900 s son puntos de partida sin medir contra endpoints reales (RISK-LIVE-02); `LiveMonitorMetrics` existe para ajustarlos.

## AD-55 — `ChannelWentOnline.initial`
**Contexto:** Al arrancar, un canal ya en directo se descubre por sondeo, no por una transición. Emitirlo igual que un go-live real dispararía "X está en directo" en cada arranque; no emitirlo haría que auto-download no capturara un directo en curso.
**Decisión:** Campo nuevo `initial: bool = False` (compatible hacia atrás). `True` solo en el **primer** avistamiento de un canal por sondeo que ya lo encuentra en directo; una notificación push (`authoritative`) es siempre transición real, aunque el canal fuera desconocido. El consumidor decide: notificaciones lo ignoran, auto-download (FASE 11) puede actuar sobre él.

## AD-56 — Correcciones retroactivas a FASE 4d / dominio (regla 0.13), todas con test de regresión
1. **`TwitchEventSubProvider`: una reconexión fallida olvidaba los canales.** `_recover_from_abnormal_disconnect` guardaba la lista de canales en una variable local y vaciaba `_subscription_ids` antes de reconectar; si abrir la conexión fallaba, el reintento conectaba pero no recreaba ninguna suscripción — canal sin monitoreo y aún reservando capacidad. Ahora viven en `_pending_resubscribe` hasta recrearse. Verificado que el test de regresión **falla contra el provider original** (queda en 2 suscripciones en vez de 4).
2. **Un fallo al obtener el detalle de `stream.online` mataba el loop de recepción** (la excepción salía de `run_forever`). Ahora se cuenta como error y no se propaga; el reconcile lo recupera (RISK-LIVE-05).
3. **`EventBus.publish`: un suscriptor que lanzaba impedía que los demás oyeran el evento** y propagaba la excepción al publicador (el monitor). Ahora cada handler se aísla y se registra.
4. **`run_forever` de EventSub no tiene manejo de errores propio** (FASE 4d, a propósito): sin supervisor, la primera desconexión irrecuperable terminaba la tarea en silencio. `supervise()` (`application/live_monitor/supervision.py`) reinicia con backoff y nunca reinicia tras un `stop()`.
5. **Bug propio de esta fase, encontrado por su test:** un wake-up obsoleto (la ráfaga de suscripciones volvía a activar el evento durante la pausa de agrupación) provocaba un segundo poll inmediato; se limpia el evento justo antes del poll.
6. **`TwitchEventSubProvider.stop()` no detenía `run_forever`:** el socket cerrado se leía como una caída anormal y el loop abría una conexión nueva. Ahora `stop()` es terminal (`_stopped`) y `run_forever` retorna.
`CapacityExceededError` ahora también es un `LiveMonitorCapacityError` (tipo de dominio), para que Application reaccione sin importar la jerarquía de errores de Twitch.

## AD-57 — Qué se monitorea y quién lo decide: `LiveMonitorService.sync()`
**Decisión:** Se monitorea un favorito con `notify_on_live` **o** `auto_download` (uno con ambos apagados no cuesta nada, §7). `sync()` reconcilia lo que vigilan los monitores con el repositorio de favoritos (idempotente, en orden de `position`: los primeros favoritos obtienen las plazas push). `stop()` es terminal para el servicio (uno detenido no se reinicia; se construye otro). Un fallo al suscribir un canal se informa en `SyncReport.failed` y se reintenta en el siguiente `sync()`; una plataforma sin monitor es `unsupported`, no un error (§9). `start()`/`stop()` corren cada monitor bajo `supervise()`.

## AD-58 — Métricas: requests/reconexiones exactos, CPU/RAM del proceso; `psutil` como única dependencia nueva
**Decisión:** `MonitorStats` (dominio) es el vocabulario común: `requests`, `polls`, `errors`, `rate_limited`, `reconnects`, `abnormal_disconnects` + gauges (`channels_watched`; `poll_interval_seconds`, que al sumar backends es el ritmo *más rápido* que realmente sondea — el que acota cuánto tarda en notarse un go-live). Cada backend cuenta lo suyo; `LiveMonitorMetrics.snapshot()` los suma y añade `cpu_percent` (entre snapshots), `rss_bytes` y `requests_per_minute`. CPU/RAM son **del proceso completo**: el SO no permite separar la parte de un monitor in-process, y el docstring lo dice. Lo no medible es `None`, nunca un número inventado. `psutil` (única dependencia nueva, solo en `infrastructure/monitoring/`, detrás del protocolo `ResourceProbe`): medir el RSS en Windows (destino confirmado, AD-10) exige otra llamada de SO que un `ctypes` a mano no podría probarse desde este sandbox.

## AD-59 — Fuera del alcance de FASE 10, a propósito (regla 0.5)
- **Debounce/anti-duplicados de notificaciones** — §22 lo asigna al `NotificationService`, no al monitor (el monitor ya deduplica *transiciones*).
- **Cableado al `Container`/ciclo de vida de la app y a los casos de uso de favoritos** — mismo criterio que RISK-ARCH-01/03: los adaptadores reales necesitan credenciales que este entorno no tiene (RISK-ARCH-05).
- **Consumidores** de `ChannelWentOnline/Offline` (notificaciones, auto-download, scheduler) — FASE 11+.
- **Sintetizar offline+online cuando `started_at` cambia entre dos polls** (stream reiniciado): no se verificó que `started_at` sea estable dentro de una sesión en Kick; sintetizar eventos sobre un supuesto sin verificar arriesga falsos positivos (RISK-LIVE-04).

## AD-60 — `RecordingService`: bug real encontrado y corregido en esta misma fase — determinar "¿está en vivo?" desde el `LiveStateTracker` de FASE 10, no desde `PlatformRegistry.get_live_stream()`
**Contexto:** AD-48 (FASE 9) ya documentó que `PlatformRegistry.get_live_stream()` depende de que la plataforma tenga un `LiveStreamProvider` de un solo canal, y que Kick no tiene uno. Al construir `RecordingService` la primera vez usé exactamente esa llamada para decidir si grabar. Ningún test unitario (con fakes de Twitch) lo detectó porque el fake de Twitch sí tenía un `LiveStreamProvider`.
**Cómo se encontró:** El test de integración de punta a punta de esta fase (`tests/test_scheduling_integration.py`), con los adaptadores reales de Kick (sin `LiveStreamProvider`, como en producción) y el motor de descargas real, fallaba con `ChannelNotLiveError` pese a que el canal sí estaba en vivo según el `LiveStateTracker`. Sin ese test — que replica exactamente lo que FASE 10 ya validó de punta a punta — el auto-download y los `ScheduledDownload` de Kick habrían quedado completamente no funcionales sin que ningún test lo señalara.
**Decisión:** `RecordingService` ahora recibe un `LiveStateTracker` y llama a `tracker.stream_of(channel_ref)` (lectura de diccionario, sin red) en vez de `await registry.get_live_stream(channel_ref)`. Esto es además más correcto que la alternativa: el tracker ya refleja el estado en el momento exacto en que se publica `ChannelWentOnline` (se actualiza antes de publicar — ver `tracker.py`), así que no hay ninguna ventana de carrera entre "me entero de que está en vivo" y "confirmo que está en vivo" que una consulta de red sí tendría.
**Consecuencias:** `RecordingService.__init__` cambió de firma (`registry, downloads, engine, planner` → `registry, live_state, downloads, engine, planner`). Sin uso en `src/` fuera de esta fase todavía (ver RISK-ARCH-05, que ahora también cubre este cableado), así que no hay compatibilidad hacia atrás que romper. Todos los tests que simulaban "el canal está en vivo" (`Env.go_live()`) pasaron de escribir en un `FakeLiveStreamProvider` a llamar `tracker.observe_live()` — igual de simple, y ahora ejercitan el mismo camino que producción.
**Regla aplicada:** Master Plan permanente "no asumir, verificar" — la verificación fue justamente construir el camino real (adaptadores reales + engine real) antes de dar la fase por cerrada, no confiar en que los fakes coincidan con el contrato real de cada protocolo.

## AD-61 — Un `ScheduledDownload` sigue siendo un favorito
**Contexto:** §20/§21 mantienen `ScheduledDownload` y `Favorite` como conceptos separados; §48 pide leer `AutoDownloadRule`/`NotificationRule` desde el favorito.
**Decisión:** `NotificationRule`/`AutoDownloadRule` (`domain/scheduling.py`) se derivan de `Favorite` con `.from_favorite()` — puras, sin estado propio. Se siguen *almacenando* como columnas de `favorites` (nada que migrar); todo consumidor decide mirando la regla derivada, nunca los flags crudos de `Favorite` directamente. `AutoDownloadRule.priority` es la `position` del favorito: el orden del usuario en su lista es también su prioridad de grabación (misma escala que `ScheduledDownload.priority` y `DownloadJob.priority`).
**Consecuencias:** Un favorito con ambos flags apagados no cuesta nada (§7) — ni monitoreo (ya en FASE 10) ni lógica de grabación.

## AD-62 — Tres disparadores con semántica propia; `AT_TIME` es la única con ventana y repetición semanal
**Decisión:** `ON_NEXT_LIVE` (una vez), `RECURRING` (cada vez que el canal entra en vivo — idéntico a `Download/ScheduledDownloadManager.py` de 3.5.5, verificado contra el código original), `AT_TIME` (hora concreta, opcionalmente semanal vía `weekdays`, con `window_seconds` de tolerancia tras la hora fijada). `ScheduledDownload.__post_init__` valida que `run_at`/`weekdays` solo se usen con `AT_TIME`. `SchedulePhase` (DISABLED/SCHEDULED/WAITING_LIVE/RUNNING/EXPIRED) se calcula siempre desde `(is_active, download_id, next_due_at, now)` — nunca se guarda, así que no puede desincronizarse de esos campos.
**Consecuencias:** Un `AT_TIME` que se crea dentro de la ventana de su propia hora de hoy se arma de inmediato (`with_first_due`), en vez de esperar una semana — evita el caso "programé una grabación diaria de las 20:00 a las 20:10 y la primera nunca se dispara".

## AD-63 — El scheduler nunca sondea: duerme exactamente hasta el próximo evento que importa
**Decisión:** `ScheduledDownloadScheduler.tick()` calcula, para cada ítem, el próximo instante relevante (hora debida, cierre de ventana, reintento pendiente) y `run_forever` duerme ese delta — nunca menos, nunca un intervalo fijo. Sin ningún ítem, no hay temporizador en absoluto: se espera un `asyncio.Event` hasta `refresh()`. El único caso donde SÍ se "consulta" es una vez por ítem armado, al momento exacto de armarse (captura un canal que ya estaba en vivo) — nunca en bucle. Acotado a `max_sleep_seconds` (60s por defecto) para que un cambio de hora del sistema o una suspensión/resume no deje al scheduler dormido más de ese margen.
**Consecuencias:** Coherente con Master Plan §20 ("El scheduler debe dormir cuando no haya trabajo") y con el mismo principio ya aplicado al Live Monitor en FASE 10 (AD-54).

## AD-64 — Recuperación de reinicio: primero el motor de descargas, después el scheduler, en ese orden
**Contexto:** §48 pide "restart recovery".
**Decisión:** Dos piezas independientes, deliberadamente en capas separadas: `RecoverInterruptedDownloadsUseCase` (nivel del motor de descargas — ni sabe qué es un `ScheduledDownload`) reconcilia cada `Download` cuya fila quedó en un estado "en vuelo" (`QUEUED/PREPARING/DOWNLOADING/PROCESSING`) al cerrar la app: un directo (`MediaKind.STREAM`) se marca `FAILED` con un mensaje claro (su URL de reproducción ya no existe — no es reanudable, ver RISK-RESUME-01 de FASE 7); un VOD/clip se re-encola (`SegmentManager` ya salta segmentos existentes en disco). Los `PAUSED` no se tocan — `DownloadService.resume()` ahora re-encola si nadie los tiene tomados en esta sesión (antes solo funcionaba si el worker seguía vivo en memoria). Luego, `ScheduledDownloadScheduler.recover()` reconcilia cada `ScheduledDownload` cuyo `download_id` apunta a una descarga que ya terminó (o desapareció) mientras la app estaba cerrada, contra el estado real de esa descarga. El orden importa: correr el motor primero convierte "interrumpido" en "FAILED" antes de que el scheduler decida si reintentar.
**Consecuencias:** El cableado real de este orden en el arranque de la app es del `Container`/ciclo de vida — fuera de esta fase (ver RISK-ARCH-05, ya ampliado a esto).

## AD-65 — Selección de calidad: la preferencia guardada nunca bloquea una grabación
**Contexto:** Puerto de `ScheduledDownloadPreset.AVAILABLE_QUALITY` (3.5.5): best/1080p/720p/480p/360p/160p/worst/solo-audio.
**Decisión:** `select_quality()` (pura) intenta, en orden: coincidencia exacta de etiqueta → misma resolución con el mejor frame rate disponible → si nada coincide, la mejor calidad de video, marcando `fell_back=True`. Nunca lanza salvo que la plataforma no ofrezca ninguna calidad en absoluto (`NoQualitiesError` → `RecordingUnavailableError`, no reintentable).
**Consecuencias:** Un favorito con preferencia "1440p" en un canal que solo llega a 1080p igual se graba (a 1080p), en vez de fallar silenciosamente — mismo comportamiento por defecto que 3.5.5 cuando "solo resolución preferida" está desactivado.

## AD-66 — Rutas de destino: la plantilla decide subcarpetas; el saneo nunca permite que un valor del usuario cruce un separador de ruta
**Decisión:** `DestinationPlanner` sanea cada *valor* (título del stream, nombre de canal, etc.) antes de sustituirlo en la plantilla — nunca al revés. Solo las barras que ya estaban en la plantilla del usuario (`FilenameTemplate`, FASE 3) generan subcarpetas; un `/` o `..` dentro de un título de stream se convierte en `_`. Nombres reservados de Windows (`CON`, `NUL`, …) y componentes vacíos también se sanean, porque el destino final confirmado es Windows (AD-10). Un nombre ya ocupado en disco, o reservado por otra descarga en vuelo (`_downloads.list_by_status` de los estados no terminales), obtiene un sufijo `(2)`, `(3)`, ...
**Consecuencias:** Cubierto por tests con valores hostiles explícitos (`../../etc/passwd`, `a/b\\c`, nombres reservados, 300 caracteres).

## AD-67 — Un ítem de scheduler puede "seguir" una grabación ya iniciada por otra cosa
**Contexto:** Un `ScheduledDownload` y una `AutoDownloadRule` pueden apuntar al mismo canal (nada lo impide ni debería impedirlo).
**Decisión:** `RecordingService.start()` usa un lock por canal; si ya hay una grabación activa para ese canal, lanza `AlreadyRecordingError(download_id)` en vez de crear una segunda. El scheduler (y `AutoDownloadService`) capturan ese caso: el scheduler adopta el `download_id` existente (`item.download_id = existing`) y espera su desenlace igual que si la hubiera empezado él; `AutoDownloadService` simplemente no hace nada (la otra parte ya la está siguiendo). Nunca dos grabaciones simultáneas del mismo canal.
**Consecuencias:** Verificado con dos `start()` concurrentes vía `asyncio.gather` (test `test_two_simultaneous_requests_produce_one_recording`).

## AD-68 — `DownloadFinished`: quién libera un canal, y quién no debe hacerlo
**Decisión:** `DownloadExecutor.run()` (antes solo `_run`, ahora un wrapper) anuncia `DownloadFinished` en el bus público cuando la descarga llega a un estado terminal — incluida una excepción inesperada, que ahora se atrapa, marca la descarga `FAILED` y se re-lanza (antes se perdía silenciosamente en el bucle del `DownloadCoordinator`, dejando la fila en `DOWNLOADING` para siempre). `asyncio.CancelledError` (apagado de la app) NO cuenta como terminal — se re-lanza sin anunciar nada, porque el estado se deja tal cual para que la recuperación de reinicio (AD-64) decida. `RecordingService.attach()` escucha ese evento para liberar `_active[channel_ref]`; el `event_bus` es un parámetro opcional del executor (`None` por defecto) — sin él, el comportamiento es exactamente el de antes de esta fase.
**Consecuencias:** Cableado real del `event_bus` al construir el executor en el `Container` — fuera de esta fase (RISK-ARCH-05).

## AD-69 — `Playlist`: renombrar, quitar y reordenar como funciones puras que devuelven un nuevo valor
**Contexto:** FASE 3 solo tenía `with_item_added`. Master Plan §49 pide rename/delete/reorder/remove además de create/add/download/import-export.
**Decisión:** `renamed()`, `with_item_removed()`, `with_items_reordered()` (domain/collections.py) siguen exactamente el patrón ya establecido por `with_item_added()`: puras, devuelven un `Playlist` nuevo, nunca mutan. `with_item_removed()` cierra el hueco de `position` (mismo invariante 0..n-1 contiguo que `with_item_added()` ya asumía) y lanza `ValueError` si el id no existe — un no-op silencioso escondería un bug del llamador. `with_items_reordered()` toma la lista *completa* del nuevo orden (como la calcularía un drag-and-drop en el cliente), no un movimiento origen→destino: hay una sola forma obviamente correcta de aplicarla, y valida que sea exactamente una permutación de los ids actuales (mismo largo, mismo conjunto) antes de aceptarla.
**Consecuencias:** `Playlist.items` sigue siendo la fuente de verdad del orden (el tuple ya está en orden de `position`), sin un campo de orden separado que pudiera desincronizarse.

## AD-70 — `PlaylistRepository.delete` + verificación explícita de que `cascade="delete-orphan"` realmente borra filas, no solo las desconecta
**Contexto:** El docstring de FASE 8 (`playlist_repository.py`) advertía explícitamente: "No domain operation removes an item yet, so removal-via-resave isn't exercised by this phase's tests" — una advertencia dejada a propósito para esta fase.
**Decisión:** Se agregó `delete()` al protocolo y a la implementación SQL (mismo patrón que `FavoriteRepository`/`ScheduledDownloadRepository`: `session.get` + `session.delete` + `commit`). Se escribieron tests que consultan la tabla `playlist_items` directamente por SQL crudo tras un `delete()` de playlist y tras un `save()` con un ítem quitado — no solo que `get()` devuelva `None`/el conteo correcto (que sería cierto incluso con filas huérfanas abandonadas), sino que la fila realmente no está.
**Consecuencias:** Confirmado: `session.merge()` con `cascade="all, delete-orphan"` sí sincroniza la colección y borra lo que ya no está presente, sin necesitar tocar la relación explícitamente antes del delete.

## AD-71 — Descarga de playlist: `PlatformRegistry` desde el diseño, no `PlaybackResolver` único — evitando reproducir RISK-ARCH-02
**Contexto:** `EnqueueDownloadUseCase` (FASE 3) toma un `PlaybackResolver` único, no `PlatformRegistry` (RISK-ARCH-02, ya documentado). Una playlist mezcla naturalmente ítems de Twitch y Kick.
**Decisión:** `EnqueuePlaylistDownloadUseCase` (nuevo, no una extensión de `EnqueueDownloadUseCase`) usa `PlatformRegistry.available_qualities()`/`.get_channel()` para despachar cada ítem según su propia plataforma — mismo patrón que `RecordingService` (FASE 11). Reutiliza `select_quality()` (FASE 11) para el fallback de calidad y `DestinationPlanner` (FASE 11) para las rutas, incluyendo protección contra colisión de nombre entre ítems de la misma tanda (cada `Download` recién guardado entra en `list_by_status` de los "en vuelo" antes de procesar el siguiente ítem, igual que `RecordingService`).
**Consecuencias:** No se tocó `EnqueueDownloadUseCase` — ese hueco sigue abierto (RISK-ARCH-02), fuera de alcance de esta fase.

## AD-72 — Fallo por ítem, nunca aborto de toda la playlist (`PlaylistDownloadReport`)
**Contexto:** Master Plan permanente: no asumir. Un ítem con metadata obsoleta (un VOD borrado, o en esta misma fase, cualquier ítem de Kick — ver AD-73) no debería impedir que el resto de la playlist se descargue.
**Decisión:** `EnqueuePlaylistDownloadUseCase.execute()` devuelve `PlaylistDownloadReport(enqueued, failed)` — mismo patrón que `SyncReport` (FASE 10) y `RecoveryReport` (FASE 11) — en vez de lanzar en el primer error. Cada fallo se captura por ítem con su razón; el resto de la playlist sigue.
**Consecuencias:** Verificado tanto a nivel de aplicación (fakes) como de punta a punta (test de integración con el motor de descargas real, ver AD-73) que un ítem fallido no bloquea a los demás ni dentro del mismo `execute()`.

## AD-73 — Hallazgo real (no un bug, una confirmación): descargar una playlist con un ítem de Kick falla hoy con "sin calidades disponibles" — Kick no tiene `PlaybackResolver` implementado
**Contexto:** AD-05 (FASE 5) planeó VOD/Clips de Kick como un `KickUnofficialAdapter` separado, marcado como no oficial. Al construir el test de integración de punta a punta de esta fase (con el motor de descargas real, siguiendo la misma disciplina que encontró el bug de AD-60 en FASE 11) se verificó que ese adaptador nunca se construyó: `infrastructure/kick/` no tiene ningún `PlaybackResolver`.
**Impacto real, hoy:** Con el `Container` cableado (aún pendiente, RISK-ARCH-05), descargar una playlist con un ítem de Kick fallaría ese ítem específico con "no playable qualities" — `report.failed` lo señala con una razón clara, el resto de la playlist (Twitch) se descarga con normalidad. No es un crash ni un bug silencioso; es exactamente la degradación elegante que Master Plan §9 pide para capacidades ausentes.
**Decisión:** No implementar `KickUnofficialAdapter` en esta fase — está fuera del alcance de FASE 12 (Master Plan lo asignó a FASE 5, y construirlo ahora sería alcance no pedido). Se deja como RISK-KICK-04, distinto de RISK-KICK-01 (que es sobre si existe cobertura oficial) porque este es sobre un adaptador que Master Plan ya decidió construir y que simplemente no se construyó todavía.
**Consecuencias:** El test de integración de esta fase (`tests/test_playlist_download_integration.py`) deja este comportamiento como regresión permanente — si algún día se implementa `KickUnofficialAdapter` sin registrarlo en el `Container`, o si se registra pero rompe algo, este test seguiría demostrando el contrato correcto de degradación.

## AD-74 — Import/export de playlist: funciones puras de dominio, sin tocar el sistema de archivos
**Contexto:** Master Plan dice "import/export si procede" (condicional, sin especificar formato).
**Decisión:** `Playlist.to_export_dict()`/`Playlist.from_export_dict()` (domain/collections.py) son funciones puras: producen/consumen un `dict` JSON-serializable (nombre + lista de media, sin ids ni timestamps — esos son ajenos a una playlist recién importada, que es una entidad nueva). Escribir ese dict a un archivo real, o leerlo de uno, es una decisión de infraestructura/UI que esta fase no toma — el mismo principio que ya separa `DestinationPlanner.plan()` (calcula una ruta) de quién realmente escribe el archivo (`DownloadExecutor`). `ExportPlaylistUseCase`/`ImportPlaylistUseCase` son la envoltura de aplicación que agrega acceso al repositorio.
**Consecuencias:** Datos malformados en `from_export_dict()` (falta un campo, un `kind`/`platform` que no es un enum válido) se traducen siempre a un único `ValueError` con mensaje claro, nunca un `KeyError`/`TypeError`/`AttributeError` crudo que exponga la forma interna del dict al llamador.

## AD-75 — `Settings`: un solo registro, siempre válido, distinto de `AppConfig`
**Contexto:** FASE 8 dejó explícitamente pendiente la tabla `settings` "hasta que una fase futura defina el primer caso de uso que la necesite — esa fase agrega la tabla y la migración entonces, con su propio protocolo de dominio primero, no al revés". FASE 13 es esa fase.
**Decisión:** `domain/settings.py`: una entidad `Settings` (no una colección — `SettingsRepository.get()` nunca devuelve `None`, siempre `Settings()` — los valores por defecto — en una instalación nueva, sin escribir una fila hasta el primer `save()`). Explícitamente distinta de `config.settings.AppConfig` (arranque del proceso, variables de entorno, existe antes de que haya una base de datos) — `Settings` es preferencia de usuario, editable en caliente, persistida como cualquier otra entidad de esta capa.
**Consecuencias:** `SqlSettingsRepository` sigue el mismo patrón sync-en-thread que el resto de `infrastructure/persistence/`; `session.merge()` con `id` fijo (`SETTINGS_ID = "default"`) hace que un segundo `save()` actualice la misma fila, nunca cree una segunda (verificado con un `COUNT(*)` explícito).

## AD-76 — Cada campo de `Settings` mapea a un knob explícito de Master Plan §50; nada inventado sin justificación
**Contexto:** §50 lista los knobs a configurar (directory, quality, format, concurrency, retry, notifications, theme, language, minimized behavior, platform options) sin especificar tipos ni rangos.
**Decisión:** Cada campo de `Settings` se ató a un knob concreto y, cuando fue posible, al nombre/semántica de algo que YA existe en el código en vez de inventar uno nuevo: `max_concurrent_downloads` espeja `DownloadCoordinator.worker_count` (misma regla `>= 1`); `retry_max_attempts`/`retry_base_delay_seconds`/`retry_max_delay_seconds` espejan `infrastructure/downloads/retry_policy.py::RetryPolicy` campo por campo; `default_quality_preference` usa el mismo vocabulario que `application.scheduling.quality.select_quality` (FASE 11); `temp_directory` corresponde al `work_dir` que `DownloadExecutor` ya recibe como parámetro; `live_monitor_poll_interval_seconds` es un override opcional de `PollingConfig.base_interval` (FASE 10, AD-54) — exactamente lo que RISK-LIVE-02 pedía poder ajustar.
**Consecuencias:** "Twitch" y "Kick" como secciones separadas del mock de UI (`SettingsPage.qml`) **no** obtuvieron campos propios en esta fase: lo único genuinamente configurable hoy que sería "específico de una plataforma" (auth/cookies) es un tema propio y distinto (ver `docs/migration-map.md`, "Browser cookies e Integrity de Twitch"), y el mecanismo de monitoreo en sí (EventSub vs. polling) es una decisión arquitectónica fija (FASE 10), no un toggle de usuario. Ningún campo de `Settings` se inventó sin una razón rastreable a Master Plan o al código ya existente.

## AD-77 — `Settings` se edita como un valor completo, no campo por campo
**Contexto:** Con ~14 campos, un caso de uso por campo sería mucho código casi idéntico sin beneficio real.
**Decisión:** `UpdateSettingsUseCase.execute(updated: Settings)` reemplaza el registro entero — el llamador (la vista de Settings) construye `updated` con `current.updated(campo=nuevo_valor)`, nunca con un `Settings(...)` armado desde cero, porque eso resetearía a default cualquier campo no mencionado. Se dejó un test que documenta exactamente esta distinción (`test_update_settings_is_a_full_replace_not_a_merge_of_unspecified_fields`), para que quede explícito y no como una sorpresa de integración futura. `ResetSettingsUseCase` es la acción "Reset to defaults" del mock de UI, un paso: `current.reset_to_defaults()` + guardar.
**Consecuencias:** `Settings.__post_init__` valida el objeto completo sin importar cuál caso de uso lo guardó — no hay validación duplicada por caso de uso.

## AD-78 — FASE 14 se ejecuta sin "packaging strategy" (FASE 19 sigue PENDING); qué se construyó y qué se dejó explícitamente como interfaz sin decidir
**Contexto:** Master Plan §51: "ENTRADA AUTÓNOMA: settings + packaging strategy." Settings está satisfecha (FASE 13); packaging strategy no — FASE 19 sigue sin empezar. El usuario pidió explícitamente continuar a esta fase de todos modos.
**Decisión:** Se separó lo que SÍ es independiente de la decisión de empaquetado de lo que NO. `UpdateChecker` (verifica origen + versión) y `UpdateDownloader` (descarga + verifica integridad) no necesitan saber nada sobre cómo se empaqueta la app — se implementaron completos. `UpdateInstaller` es un protocolo de dominio con una única implementación concreta, `DirectoryBackupInstaller` (infrastructure/updates/installer.py): respaldo del directorio de la app, extracción de un zip, restauración automática ante cualquier fallo. Es una estrategia razonable para "un directorio de archivos", no una decisión final — un instalador específico del SO (MSI, un bundle firmado de macOS, etc.), una vez que FASE 19 decida, la reemplaza sin tocar `UpdateService` ni el protocolo `UpdateInstaller`.
**Consecuencias:** Nada de esto asume un formato de empaquetado final. Ver RISK-ARCH-07.

## AD-79 — Verificación de origen: firma Ed25519 sobre los campos que importan, no solo HTTPS
**Contexto:** Master Plan §51: "Verificar: origen; integridad; versiones". HTTPS por sí solo protege el transporte, no protege contra un servidor de actualizaciones comprometido (CDN, DNS, o la cuenta del hosting) sirviendo un manifiesto malicioso con TLS válido — el ataque de cadena de suministro clásico contra actualizadores automáticos.
**Decisión:** El manifiesto (JSON) va firmado con Ed25519; la firma cubre exactamente `f"{version}|{download_url}|{sha256}|{size_bytes}"` — los campos que importan para la seguridad — y NO cubre `release_notes`/`published_at` (cosméticos, pueden editarse sin re-firmar). `ManifestUpdateSource` rechaza cualquier manifiesto que no verifique contra la clave pública embebida en la app, y solo acepta el host fijo configurado (`infrastructure/updates/config.py::MANIFEST_URL`) — nunca sigue una redirección a otro host. Se agregó `cryptography` como dependencia nueva (única forma razonable de implementar esto correctamente; mismo criterio que agregar `psutil` en FASE 10).
**Consecuencias:** La clave pública embebida en `config.py` es un par de claves Ed25519 real, generado para este propósito — pero es una clave de **desarrollo/pruebas**, no la clave de release del proyecto. Antes de cualquier release real, `PUBLIC_KEY_PEM` debe reemplazarse por la clave pública real, y la clave privada correspondiente debe vivir solo en la herramienta de firmado de releases (nunca en este repositorio). Ver RISK-ARCH-07.

## AD-80 — Verificación de versión: nunca "distinta", siempre "más nueva" — protege contra un downgrade con manifiesto viejo pero válidamente firmado
**Contexto:** Un atacante que capturó un manifiesto viejo, legítimamente firmado, para una versión con una vulnerabilidad conocida, podría reproducirlo (replay) para engañar a la app y hacerla "actualizar" hacia atrás.
**Decisión:** `domain/version.py::Version` (comparador semver puro, sin dependencias) — `UpdateChecker.check()` solo reporta una actualización disponible si `manifest.version > current_version`, estrictamente. Una versión igual o anterior (incluida una pre-release de la versión actual) nunca se reporta como actualización.
**Consecuencias:** Ningún formato de versión fuera de `MAJOR.MINOR.PATCH[-prerelease]` es válido — coincide con el propio campo `version` de `pyproject.toml`.

## AD-81 — `UpdateService` nunca comparte workers ni cola con el motor de descargas del usuario; el paso de instalación se bloquea explícitamente si hay descargas en vuelo
**Contexto:** Master Plan §51, restricción explícita y literal: "No interferir con descargas activas."
**Decisión:** `UpdateDownloader` (el artefacto de actualización) usa su propio `httpx.AsyncClient` independiente — nunca pasa por `DownloadQueue`/`DownloadCoordinator`/`DownloadExecutor` (FASE 7), así que descargar la actualización nunca compite por un worker con una descarga del usuario, por construcción. `UpdateService.install()` sí verifica activamente `DownloadRepository.list_by_status()` contra los mismos estados "en vuelo" que `RecordingService`/`EnqueuePlaylistDownloadUseCase` ya usan (FASE 11/12) — porque instalar (reemplazar archivos de la app, potencialmente reiniciarla) sí es destructivo para una descarga en curso, aunque descargar el artefacto de la actualización no lo sea. Lanza `DownloadsInProgressError` en vez de esperar o encolar — la decisión de cuándo reintentar queda del lado del llamador.
**Consecuencias:** Verificado con un `Download` real (no un fake) en una base de datos real, en el test de integración de esta fase.

## AD-82 — Codec legacy: solo decodificación, sin ninguna dependencia de PyQt6 ni de módulos de TwitchLink; `LegacyObject` en vez de instancias reconstruidas
**Contexto:** `AppData/EncoderDecoder.py` (legacy) usa un formato JSON con tags propios (`"str:"`, `"datetime:"`, `"obj:<módulo>:<Clase>"`, `"tuple"`, etc.) y su `Decoder` reconstruye instancias reales de las clases legacy vía `importlib.import_module`. Master Plan §0.9: Twick Hub debe tratarse como un proyecto completamente independiente; `tests/domain/test_no_pyside6_import.py` ya confirma que ninguna parte de Twick Hub depende de PyQt6/PySide6.
**Decisión:** `infrastructure/migration/legacy_codec.py` reimplementa el `Decoder` campo por campo pero se detiene un paso antes: un blob `obj:...` decodifica a `LegacyObject(type_name, fields)` — una bolsa de campos ya decodificados, nunca una instancia real de la clase legacy. Nunca importa `PyQt6` ni ningún módulo de `TwitchLink`/`Services.*`. Fechas se parsean con `datetime.fromisoformat` puro (sin `QDateTime`); un `"timezone:<id>"` decodifica al id de zona como string plano (sin `QTimeZone`).
**Consecuencias:** El codec no necesita que el código legacy esté siquiera instalable para funcionar — solo necesita el archivo `settings.json`. Un tag desconocido o un blob `tuple`/`obj` malformado levanta `LegacyCodecError` explícito en vez de fallar con un `KeyError`/`AttributeError` críptico. Verificado con un fixture sintético completo (los 9 tipos de tag, incluyendo los casos límite de `datetime` vacío y con distintos offsets) más 26 casos de test en `tests/infrastructure/migration/test_legacy_codec.py`.

## AD-83 — Detect/backup: ruta por SO idéntica a `Config.py`; el archivo original nunca se muta; el secreto no se purga del legacy — ver RISK-MIGRATION-01
**Contexto:** `Core/Config.py` (legacy) resuelve `APPDATA_PATH` vía `OSUtils.getSystemAppDataPath() / "TwitchLink"`; auditados ambos `OSAdapter` (`Windows.py`: `%APPDATA%`; `MacOS.py`: `~/Library/Application Support`) — confirmado que **no existe** adapter de Linux (`OSUtils = WindowsUtils if isWindows() else MacOSUtils`, sin rama Linux). Master Plan, regla permanente: "No romper datos del usuario." `docs/risk-register.md::RISK-SEC-01` pedía además "migrar y purgar el valor legacy, no solo dejar de escribirlo desde ese punto en adelante."
**Decisión:** `infrastructure/migration/legacy_locator.py::detect()` replica exactamente esas dos rutas y devuelve "no encontrado, sin ruta conocida" en Linux (nunca inventa una ruta no oficial). `backup()` copia el archivo byte a byte a un destino con timestamp (nunca sobrescribe un backup anterior) y verifica el tamaño resultante; **nunca abre el original para escritura**. Se decidió **no purgar** el secreto del `settings.json` legacy original pese a lo que sugiere RISK-SEC-01: hacerlo mutaría un archivo de una aplicación de terceros que el usuario podría seguir usando activamente (TwitchLink legacy en paralelo), lo cual entra en conflicto directo con la regla permanente más fuerte ("no romper datos del usuario"). Se prefirió: migrar el secreto al credential store de Twick Hub (cumple la parte no condicional del requisito de Master Plan §52, "Secretos: credential store, nunca JSON/SQLite" — sobre el almacenamiento de Twick Hub, no sobre mutar el archivo ajeno) y dejar la purga como acción explícita, no implementada en esta fase.
**Consecuencias:** RISK-SEC-01 se actualiza para reflejar esto exactamente (migración sí, purga del original no). Nuevo hallazgo, no anticipado al planear esta fase: el propio backup que este módulo crea es **también** una copia en texto plano del secreto, sin cifrar, ahora viviendo en el directorio de datos de Twick Hub — ver RISK-MIGRATION-01.

## AD-84 — Idempotencia y reversibilidad: hash del archivo como llave de ejecución completa, ids deterministas (uuid5) por ítem, y el único hueco real de `rollback()`
**Contexto:** Master Plan §52 pide explícitamente un "migrador reversible/idempotente." Favorites/ScheduledDownload/Download no tienen ningún concepto de "vino de una migración" en su propio modelo de dominio — no se les iba a agregar un campo así solo para esta fase (Master Plan §0.5, alcance).
**Decisión:** Dos mecanismos de idempotencia, en capas distintas. (1) Nivel de ejecución completa: `LegacyMigrationRun.source_sha256` (SHA-256 del archivo crudo) es la llave — `LegacyMigrationRunRepository.find_by_source_hash()` permite que una segunda corrida contra un archivo byte-idéntico que ya completó (con o sin warnings) devuelva la misma corrida sin leer ni escribir nada de nuevo. (2) Nivel de ítem: cada favorito/scheduled-download/download migrado recibe un id determinista (`uuid5`, nunca `uuid4`) derivado de un campo identificador estable del dato legacy (el `external_id` del canal para scheduled downloads; tipo+id+timestamp de inicio para el historial) — así, `repository.save()` (que hace upsert por id vía `session.merge()`) es un no-op real en una segunda corrida, incluso si el hash completo del archivo cambió por otro motivo. `LegacyMigrationRun` registra qué ids creó *esta* corrida específicamente (no "todo lo migrado"), que es lo que permite a `rollback()` deshacer solo lo suyo sin tocar algo que ya existía de antes.
**Consecuencias — el hueco real:** `rollback()` deshace favoritos, scheduled downloads, el token del credential store, y restaura `Settings` a su snapshot exacto previo a la migración (guardado en `previous_settings_json` en el momento de migrar, no reconstruido después). **No** deshace el historial de descargas migrado: `DownloadRepository` no tiene — ni tenía antes de esta fase, en ningún otro punto de la aplicación — una operación `delete()`, porque el historial de descargas se trata en el resto de la app como un registro de solo-append. Agregar `delete()` únicamente para el rollback de esta fase habría sido exactamente el tipo de capacidad inventada que Master Plan §0.5 prohíbe. Ver RISK-MIGRATION-02 — "reversible" es, honestamente, parcial por diseño, no total.

## AD-85 — `Settings` se fusiona sobre la fila existente, nunca la reemplaza entera; `StreamHistory` como fuente representativa de directorio/formato por defecto; gaps documentados sin inventar campos nuevos
**Contexto:** Legacy no tiene un único directorio/formato de descarga: `Temp._downloadOptionHistory` guarda un directorio y formato **separados** por tipo de contenido (`StreamHistory`, `VideoHistory`, `ClipHistory`, `ThumbnailHistory`, `ScheduledDownloadHistory`). `Settings` (FASE 13) solo tiene un `default_directory`/`default_format` global. Legacy tampoco persiste ninguna preferencia de calidad global (`Quality` solo aparece elegida por ítem, nunca guardada como preferencia).
**Decisión:** `legacy_transform.settings_overrides_from_legacy()` produce un `dict` de overrides que se aplica con `existing.updated(**overrides)` (nunca `Settings(**overrides)` desde cero) — cualquier campo que Twick Hub tenga y legacy no (p. ej. `live_monitor_poll_interval_seconds`) queda intacto. `StreamHistory` se eligió como la fuente representativa para `default_directory`/`default_format` (streams es la funcionalidad insignia de ambos proyectos); `VideoHistory`/`ClipHistory`/`ThumbnailHistory`/`ScheduledDownloadHistory` con un directorio/formato distinto **no** se migran individualmente — es una pérdida de fidelidad deliberada, no un descuido. `default_quality_preference` se deja completamente intacto (sin fuente legacy global de la cual migrarlo).
**Consecuencias — gaps confirmados y documentados, ninguno inventado como campo nuevo:** plantillas de nombre de archivo por tipo (`Templates.streamFilename/videoFilename/clipFilename` — Twick Hub no tiene ningún campo de plantilla configurable todavía en `Settings`/`Favorite`/`ScheduledDownload`, solo un `DEFAULT_TEMPLATE` fijo en `DestinationPlanner`, FASE 11); huso horario (`Localization._timezone` — sin campo equivalente en `Settings`); el interruptor `Advanced._searchExternalContent`; y `General._openProgressWindow` (estado de UI de la app legacy, sin equivalente ni necesidad de tenerlo). Ver RISK-MIGRATION-03.

## AD-86 — Favoritos y scheduled downloads necesitan resolución de canal en línea (login → id numérico); el historial de descargas no
**Contexto:** Legacy guarda bookmarks (`General._bookmarks`) y el canal de un `ScheduledDownloadPreset` como el **login en texto plano**, nunca el id numérico de Twitch. `PlatformRef.external_id` en Twick Hub, en cambio, siempre es el id numérico (confirmado en `infrastructure/twitch/gql/mappers.py`) — nunca el login. En cambio, cada entrada de `Temp._downloadHistory` ya trae embebido el objeto GQL completo (`content.broadcaster`/`content.owner`, con su `id` numérico) tal como se cacheó en el momento de la descarga original.
**Decisión:** `LegacyMigrationService` resuelve bookmarks/scheduled-download logins vía `PlatformRegistry.channel_directories[Platform.TWITCH].find_channel(login)` (una llamada de red real, por ítem) antes de poder migrarlos — si no hay `PlatformRegistry` inyectado, o no hay `ChannelDirectory` de Twitch registrado ahí, o el login específico no resuelve, ese ítem se registra en `skipped_bookmark_logins`/`skipped_scheduled_download_logins` con una advertencia, nunca se descarta en silencio ni bloquea el resto de la corrida. El historial de descargas, en cambio, se migra **sin ninguna dependencia de red**, siempre, usando directamente el id numérico ya embebido en el propio registro legacy.
**Consecuencias:** No se pudo validar `find_channel()` contra la API real de Twitch en este sandbox (sin acceso a red) — mismo límite que RISK-LIVE-01/RISK-KICK-03 de fases anteriores. Ver RISK-MIGRATION-04.

## AD-87 — Índice de calidad/frame-rate: tabla fija portada literal de `ScheduledDownloadPreset.AVAILABLE_QUALITY`; la preferencia de frame-rate no tiene destino y se descarta
**Contexto:** `ScheduledDownloadPreset` (legacy) no guarda una calidad como valor — guarda `preferredQualityIndex`/`preferredFrameRateIndex`, índices enteros dentro de una lista fija que solo existe como constante en el código fuente legacy, nunca serializada junto al índice.
**Decisión:** `_LEGACY_QUALITY_INDEX = ("best", "1080p", "720p", "480p", "360p", "160p", "worst", "audio-only")` en `legacy_reader.py` es exactamente ese orden, portado como comportamiento (Master Plan §0.9), no re-derivado — coincide además con el vocabulario que `application.scheduling.quality.select_quality` (FASE 11, AD-76) ya espera. Un índice fuera de rango se degrada a `"best"` con una advertencia explícita en vez de lanzar.
**Consecuencias:** `preferredFrameRateIndex` (HIGH/LOW) no tiene ningún campo destino en `ScheduledDownload` — `quality_preference` como string único no distingue "mejor resolución, cualquier fps" de "mejor resolución, el fps más bajo disponible". Se descarta sin intentar aproximarlo, en vez de inventar una heurística no pedida. Ver RISK-MIGRATION-03.

## AD-88 — FASE 16 corrió `pytest`/`ruff`/`pyright` reales por primera vez desde FASE 8, retirando RISK-MIGRATION-05
**Contexto:** Esta sesión es la primera de este linaje de sandboxes con acceso real a PyPI. Antes de escribir una sola línea de FASE 16, se instaló el proyecto (`pip install -e ".[dev]"` en un venv nuevo) y se corrió la suite completa acumulada de FASE 8 a FASE 15, tal como pedía `NEXT_PHASE_PREREQUISITES` del `phase-state.md` de FASE 15.
**Decisión:** Tratar esa verificación como un prerrequisito de facto de FASE 16, no como parte de su alcance funcional — y corregir en el momento cualquier fallo real encontrado (no solo reportarlo), porque dejarlo para "una fase futura con red" habría repetido el mismo aplazamiento indefinido que ya llevaba desde FASE 8.
**Resultado:** 958/958 tests pasando; Alembic real (`upgrade head`/`downgrade base`) limpio contra la cadena completa FASE 8→15; `ruff` pasó de nunca ejecutado a 0 errores propios del proyecto (8 `E501` restantes son autogenerados en `migrations/versions/`, misma convención que AD-43 ya aceptó para pyright); `pyright` pasó de 30 errores reales a 0. Todos los fixes fueron quirúrgicos: 3 `pytest.raises(Exception)` reemplazados por el tipo real que cada camino lanza (`LegacyValidationError`/`LegacyCodecError`), un `assert` de invariante ya garantizado por el flujo, un `None`-check explícito, y tipado (`dict[str, Any]`) de dos test-helpers — ninguno cambió comportamiento de producción.
**Consecuencias:** RISK-MIGRATION-05 se cierra por completo. RISK-MIGRATION-04 (red real hacia Twitch) sigue abierto — este sandbox tiene red hacia PyPI/GitHub/npm pero no hacia twitch.tv/kick.com (ver RISK-PERF-04, nuevo en esta fase, mismo patrón).

## AD-89 — FASE 16 mide contra un "workload reproducible" sintético local, no contra Twitch/Kick reales
**Contexto:** El índice del Master Plan exige "aplicación actual + workload reproducible" como prerrequisito de FASE 16; ningún workload de este tipo existía todavía, y este sandbox no tiene red hacia twitch.tv/kick.com para generar uno con datos reales.
**Decisión:** Construir el workload con las mismas piezas reales del proyecto conectadas a extremos locales en vez de a Twitch/Kick: un servidor HTTP local (stdlib `http.server`) sirviendo una playlist HLS real y 6 segmentos `.ts` reales (codificados con `ffmpeg`, patrón `testsrc`, ~62 KB cada uno) para ejercitar el `DownloadExecutor` real completo (`HlsPlaylistReader` + `HttpxSegmentFetcher` + `SegmentManager` + `FFmpegProcessor` con `ffmpeg` real vía subprocess); y un servidor `websockets` local para ejercitar el `TwitchEventSubProvider` real (solo se inyecta el conector para apuntar al servidor local, el resto del código de reconexión/keepalive es el de producción). El polling de Kick reutiliza el bench ya existente de FASE 10 (`live_monitor_bench.py`), no se reinventa.
**Alternativas descartadas:** Simular todo con fakes/mocks de más alto nivel (más rápido de escribir, pero mediría el overhead de los fakes, no del pipeline real — no cumple "workload reproducible" del Master Plan). Esperar a una sesión con red hacia Twitch/Kick (indefinido, y FASE 16 no puede quedar bloqueada por eso — ver AD-88 sobre el mismo patrón de aplazamiento).
**Consecuencias:** Los números de CPU/RAM/tiempo son reales para el código del proyecto bajo carga real, pero no reflejan latencia de red real ni comportamiento bajo condiciones reales de Twitch/Kick (RISK-PERF-04). El arnés queda en `benchmarks/fase16_performance_audit.py`, reutilizable por fases futuras y extensible cuando haya thumbnail cache real que medir (RISK-PERF-02).

## AD-90 — FASE 17: `KickOAuthFlow.revoke()` mueve el token de la query string al cuerpo del POST
**Contexto:** Auditoría de FASE 17 (tokens/network/secret leakage). `revoke()` mandaba `{"token": token, "token_hint_type": ...}` como `params=` (query string) al endpoint de revocación de Kick. Un secreto en la URL es estructuralmente más propenso a terminar en un log de acceso de un proxy TLS-terminating, en el log de debug de `httpx`/`urllib3`, o en `str(exc)` de cualquier error HTTP levantado sobre esa request (que incluye la URL completa) — nada de eso ocurre igual con un valor en el cuerpo de la petición.
**Decisión:** Cambiar `params=` por `data=` (form-encoded en el cuerpo). RFC 7009 (OAuth 2.0 Token Revocation) especifica el token como parámetro del cuerpo precisamente por esto — no es una desviación de lo que documenta Kick, es alinear con el estándar que Kick dice implementar.
**Consecuencias:** `tests/infrastructure/kick/test_oauth_flow.py::test_revoke_sends_token_in_request_body_not_url` reemplaza el test anterior (que afirmaba el comportamiento inseguro como esperado) y verifica explícitamente que el token NO aparece en `request.url`. `tests/infrastructure/kick/test_account_service.py::test_disconnect_revokes_and_deletes` se actualizó para leer el token del cuerpo de la petición en vez de `request.url.params`. Ningún cambio de comportamiento observable para quien llama a `revoke()` — mismo endpoint, mismo resultado, el secreto solo viaja distinto.

## AD-91 — FASE 17: `IntegrityAdapter._begin_capture` gana un guard `_SettleOnce` contra una carrera timeout-vs-interceptor tardío
**Contexto:** Auditoría de FASE 17 (race conditions, duplicate events, "revisar especialmente: Twitch integrity"). `_begin_capture` tenía tres desenlaces posibles (timeout, señal `intercepted` del interceptor Chromium, respuesta de la petición de red que ese interceptor dispara) sin exclusión mutua entre ellos: `QWebEngineUrlRequestInterceptor.interceptRequest` corre en el hilo IO de Chromium, así que la señal `intercepted` cruza a una conexión Qt en cola (`Qt::QueuedConnection` implícito) hacia el hilo de la GUI — puede entregarse *después* de que `_on_timeout` ya haya resuelto la captura (`callback(None)`) y empezado a destruir `page`/`profile` vía `deleteLater()`. Sin guard, esa entrega tardía dispara una segunda petición POST real a `INTEGRITY_URL` con el `Authorization: OAuth <token del usuario>` adjunto — una repetición de red no solicitada que carga un secreto — y podría invocar `callback` una segunda vez.
**Decisión:** `_SettleOnce`, una clase mínima y sin dependencias (`settle()` devuelve `True` solo la primera vez), comparte estado entre los tres desenlaces (`_on_timeout`, `_on_intercepted`, `_on_reply_finished`); cada uno comprueba el guard antes de actuar. `_cleanup()` además desconecta explícitamente `interceptor.intercepted` y `timeout_timer.timeout` (en vez de confiar solo en `deleteLater()`, que no tiene efecto retroactivo sobre una señal ya encolada) para que una entrega tardía no tenga ya ningún slot al que llamar.
**Consecuencias:** No se pudo ejercitar `_begin_capture` de punta a punta en este sandbox (mismo límite ya documentado en el docstring del módulo: sin Chromium sandboxeable como root, sin red hacia Twitch). `_SettleOnce` en sí — la pieza que efectivamente cierra la carrera — es Python puro y se probó de forma aislada en `tests/infrastructure/twitch/test_integrity_token.py` (3 casos nuevos). El resto de la corrección (el guard efectivamente conectado en los tres puntos de `_begin_capture`) queda verificado por inspección de código, no por test automatizado — documentado como tal, no asumido como PASS.

## AD-92 — FASE 17: hardening menor en `redirect_listener.py` y `browser_cookie_import.py`
**Contexto:** Auditoría de FASE 17 (orphan processes/threads; path traversal en "browser cookie import", nombrado explícitamente por el Master Plan).
**Decisión (redirect_listener):** `server.timeout` (antes `None`, es decir bloqueo indefinido en `select()`) se fija ahora al mismo `timeout` que ya recibía `wait_for_callback`, y `server_close()` va seguido de un `thread.join(timeout=...)` acotado — antes el hilo en background quedaba sin unir (`daemon=True` lo cubre solo para la salida del proceso, no para una sesión larga con reintentos de OAuth). `LocalHttpRedirectListener` sigue sin cablearse a `bootstrap/dependencies.py` (confirmado — no es código muerto por accidente sino un hallazgo de RISK-ARCH-01/el patrón ya conocido de Kick OAuth no conectado a la UI real todavía), así que este hardening no tiene ningún camino de ejecución real hoy, pero deja el componente correcto para cuando sí lo tenga.
**Decisión (browser_cookie_import):** `import_session_token` ahora resuelve `profile.key` contra el directorio de datos de Firefox y rechaza (antes de importar `selenium`, y antes de lanzar un Firefox real) cualquier resultado que quede fuera de ese directorio — cubre un `profiles.ini` corrupto o manipulado con un `Path=../../..` que, sin este guard, apuntaría un Firefox real y en ejecución a un directorio de perfil arbitrario del sistema.
**Consecuencias:** `tests/infrastructure/kick/test_redirect_listener.py` (sin cambios, pasa igual — los tiempos de los 3 tests existentes ya eran compatibles con un `server.timeout` acotado). `tests/infrastructure/twitch/test_browser_cookie_import.py` gana 2 casos de traversal POSIX (`../../../../etc`, `/etc/passwd`) y 1 caso de "no falso positivo" con una key legítima; un tercer caso con separador `\` (estilo Windows) se documentó como no verificable en este sandbox Linux — `\` no es separador de ruta ahí — en vez de incluirse como un test que no prueba lo que dice probar.
